# Требования к мониторингу: req_mon

Документ-контракт. Любой **новый сервис или задача на хосте** считается принятым в
эксплуатацию только после выполнения требований ниже. Его же удобно целиком отдавать
исполнителю (человеку или ИИ) вместе с задачей: «сделай X, требования к мониторингу —
req_mon.md».

Область действия: один хост, на котором стоит этот комплект. Канал тревог — Telegram.
Реализация слоёв — `ops/monitoring/` в репозитории `stack-radar`.

---

## Почему это обязательно

11 сентября `stack-radar` упал с ошибкой Postgres и перезапустился. Узнали об этом
через сутки, случайно. `check_approvals.sh` из `wiki_visualizer` перестал писать в лог
в 12:37 — заметили только при инвентаризации. Оба отказа невидимы, потому что сервис
подключали к хосту, а к мониторингу — нет. Требования ниже закрывают ровно этот разрыв.

---

## Обязательные требования

### R1. Сервис объявлен как systemd-юнит

Никаких `nohup`, `screen`, `&` в фоне. Только юнит: у него есть состояние, автозапуск,
журнал и точка подключения тревог.

    [Service]
    Restart=on-failure
    RestartSec=10

    [Unit]
    OnFailure=alert@%n.service

Строка `OnFailure` ставится drop-in файлом, а не правкой чужого юнита:

    sudo mkdir -p /etc/systemd/system/<юнит>.service.d
    printf '[Unit]\nOnFailure=alert@%%n.service\n' \
      | sudo tee /etc/systemd/system/<юнит>.service.d/onfailure.conf
    sudo systemctl daemon-reload

### R2. Задача по расписанию запускается через runjob.sh

Любая строка в crontab оборачивается:

    <расписание> /opt/monitoring/runjob.sh <имя-задачи> -- <команда> >> <лог> 2>&1

Имя задачи — короткое, латиницей, без пробелов; оно же попадает в `job_runs` и в текст
тревоги. Редирект в лог сохраняется: обёртка пропускает вывод насквозь.

### R3. Задача зарегистрирована в реестре ритма

Без записи в `job_schedule` пропуск запуска не отслеживается — задача может тихо
перестать запускаться, и никто не узнает.

    insert into job_schedule (job, interval_min, note)
    values ('<имя>', <интервал в минутах>, '<проект: что делает>')
    on conflict (job) do update
       set interval_min = excluded.interval_min, note = excluded.note;

Правило тревоги: нет удачного прогона дольше двух интервалов — предупреждение,
дольше четырёх — тревога.

### R3-bis. Задача запускается от того пользователя, который читает её секреты

Строка crontab пользователя `ubuntu`, которой нужен `/etc/stack-radar.env` (права
`640 root:<app>`), обязана вызывать команду через `sudo -u <app> -H bash -lc`.
Иначе `Permission denied`, а за ним `unauthorized` — и задача падает каждый запуск.
Проверка при сдаче: запустить строку из crontab **дословно**, а не её содержимое из своей
сессии, где переменные уже загружены.

### R4. Ошибка обязана давать ненулевой код возврата

Скрипт, который поймал ошибку и написал о ней в лог, но вышел с кодом 0, для
мониторинга исправен. Это главный источник невидимых отказов.

    set -euo pipefail

Каждая ветка обработки ошибки заканчивается `exit 1` (или своим кодом). Проверка
перед сдачей: сломать зависимость (убрать токен, выключить сеть) и убедиться, что
`echo $?` не ноль.

### R5. Время выполнения меньше интервала запуска, повторный запуск исключён

Задача с интервалом 30 минут не имеет права идти 40. Если может — `timeout` и `flock`:

    <расписание> /opt/monitoring/runjob.sh <имя> -- \
      flock -n /tmp/<имя>.lock timeout 20m <команда> >> <лог> 2>&1

### R6. Лог пишется в файл и включён в ротацию

Лог — в `/home/ubuntu/<проект>/logs/` или рядом с проектом. Фрагмент добавляется в
`/etc/logrotate.d/bds-projects`: еженедельно, 8 копий, порог по размеру, обязательно
`copytruncate` — иначе работающая задача продолжит писать в удалённый файл.

### R7. Секреты в отдельном env-файле, не в коде и не в git

`/etc/<сервис>.env`, права `640`, владелец `root:<группа сервиса>`. В юните —
`EnvironmentFile=`. В репозитории лежит только `*.env.example` с пояснением каждой
переменной и пустыми значениями.

### R8. Есть проверка живости одной командой

Для сервиса — HTTP-эндпоинт на `127.0.0.1` либо команда, дающая ненулевой код при
неисправности. Проверка добавляется в `check.sh` строкой `note`:

    note "<ключ>" "$(grade "$значение" <warn> <crit>)" "<что показать>" "<команда для разбора>"

Ключи именуются по типу: `unit:<юнит>`, `job:<задача>`, остальное — одним словом.

### R9. Порт наружу не открывается

Сервис слушает `127.0.0.1`. Доступ снаружи — только через nginx с TLS и паролем.
Правило в security group добавляется одновременно с сервисом и удаляется вместе с ним:
открытый порт без слушателя (как 5678 от n8n) — это дыра, а не наследие.

### R10. Код и конфигурация под git

Развёртывание воспроизводится из репозитория. Правки прямо на хосте допустимы только
как временная мера и в тот же день возвращаются в репозиторий. Каталог, живущий в
одном экземпляре на диске EC2, приёмку не проходит.

### R11-bis. Гейт тестов — `npm run test:unit`

Полный `npm test` начинается с прогона скриптов платформы Grok (`brand-check`, `grok-pwa`,
og-инъекция): вне среды Grok они падают, а `&&` обрывает цепочку — тесты приложения после них
не запускаются вовсе, и зелёный экран ничего не значит. Гейт перед выкладкой — `npm run test:unit`,
и запускать его надо в чистом окружении: с загруженным `/etc/stack-radar.env` два теста
`gate-identity` падают из-за `VITE_AUTH_ENABLED=false`, хотя к приложению это отношения не имеет.

### R11. Отправка в служебный чат — только в тему

Все проекты пишут в супергруппу WikiArticles_auto. Общий конфиг —
`/etc/bds-telegram.env` (644, секретов нет): `BDS_SERVICE_CHAT_ID`, темы
`BDS_TOPIC_NEWS` 615, `BDS_TOPIC_WIKI` 619, `BDS_TOPIC_LOGS` 620 и
`BDS_ADMIN_USER_ID`. Отсюда, а не из трёх мест по проектам.

- Каждая отправка указывает `message_thread_id`; пустое значение не передаётся вовсе —
  в General тему указывать нельзя. Тревоги и сводки идут в тему Логи.
- Каждый поллер `getUpdates` фильтрует по трём условиям сразу: чат, тема, отправитель.
  Боты — админы группы, а админу Telegram отдаёт все сообщения чата независимо от
  privacy mode. Курсор двигается до фильтра.
- `getUpdates` руками для бота с работающим поллером запускать нельзя: очередь одна,
  ручной вызов уводит апдейты у поллера. Для диагностики — лог поллера, для
  экспериментов — отдельный бот.
- Удаление — `deleteMessages`, до 100 id за вызов, только сообщения моложе 48 часов.
- Бот, которым шлёт сервис, обязан состоять в группе. Проверка: `getChat` его токеном —
  «chat not found» означает, что бота в группе нет.
- Код в контейнере не видит `/etc` хоста: конфиг прокидывается
  `--env-file /etc/bds-telegram.env`, а сам образ пересобирается после правки скриптов.

## Пороги по умолчанию

| Что | Предупреждение | Тревога |
|---|---|---|
| Задача не отработала успешно | 2 интервала | 4 интервала |
| Длительность прогона | 1.5× от обычной | больше интервала |
| Ошибки в журнале (приоритет err) за час | > 10 | > 60 |
| Свободное место на диске | занято > 75% | > 88% |
| Доступная память | < 300 МБ | < 120 МБ |
| Ответ HTTP-проверки | не ожидаемый код | нет ответа |

Свои пороги задаются в том же виде и объясняются одной строкой — почему именно такие.

## Чек-лист подключения

1. Код в репозитории, секреты в `/etc/<сервис>.env` (R7, R10).
2. Юнит с `OnFailure` **или** строка crontab через `runjob.sh` (R1, R2).
3. Запись в `job_schedule` для задачи по расписанию (R3).
4. Фрагмент в `/etc/logrotate.d/bds-projects` (R6).
5. Проверка живости в `check.sh`, если сервис долгоживущий (R8).
6. Проверка, что ошибка даёт ненулевой код (R4).
7. Прогон `sudo /opt/monitoring/check.sh` — новый ключ виден и в состоянии `ok`.

Подключение считается работающим только после пункта 7. Не «настроено», а
«проверено»: сломайте зависимость и убедитесь, что тревога пришла в Telegram.

## Что мониторинг НЕ покрывает

- Скиллы и плагины, которые запускаются в сессии Claude (например `wiki-scout`) — у них
  нет процесса на хосте. Их отслеживают по свежести результата, а не по прогону.
- Качество результата: задача может отработать с кодом 0 и сделать ерунду. Это зона
  проверок внутри самой задачи.
- Внешние сервисы (Telegram, xAI, GitHub). Их отказ виден как ошибка задачи, отдельной
  проверки доступности нет.
